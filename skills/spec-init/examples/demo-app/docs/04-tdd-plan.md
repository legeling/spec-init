# TDD Plan: Demo App

> 更新时间：2026-04-29
>
> 先定义如何证明正确，再开始大规模实现。

## 1. 测试目标

- 先验证初始化脚本能稳定生成关键文件
- 先验证文档模板之间的追踪关系没有断链

## 2. 测试层次

| 层次 | 目标 | 覆盖内容 | 工具 / 方式 |
|---|---|---|---|
| Unit | 验证模板替换和参数处理逻辑 | 项目名、类型、日期替换 | shell / diff 检查 |
| Integration | 验证脚本运行后完整骨架生成 | docs、README、AGENTS、占位目录 | Bash 执行脚本 |
| E2E | 验证用户从想法到首批任务的完整路径 | intake -> requirements -> design -> tdd -> tasks | 人工 walkthrough + 示例文档 |

## 3. 需求到测试映射

| Test ID | Requirement | Test Type | 核心断言 |
|---|---|---|---|
| `TEST-001` | `FR-001` | Integration | 运行脚本后应生成全部核心文件 |
| `TEST-002` | `FR-002` | E2E | 模板中应显式写出“该写什么”和“不该写什么” |
| `TEST-003` | `FR-003` | E2E | 示例文档中至少存在一条完整追踪链 |

要求：

- 每个高优先级 `FR-*` 至少映射到一种自动化测试
- 如果某条需求暂时不能自动化验证，要写清原因和替代验证方式

## 4. 第一批红灯测试

1. 运行初始化脚本后缺少 `AGENTS.md`
2. requirements 模板没有“不要写技术实现”的提示
3. 示例里找不到 `FR -> DES -> TEST -> T` 链路

## 5. 测试数据与夹具

- 一个空目录作为初始化目标
- 一个已有 README 的目录用于验证“默认不覆盖”行为

## 6. 回归策略

- 初始化脚本路径处理、模板变量替换和目录生成必须保留回归测试
- 任何模板边界改动都要补文档回归检查
- 模板结构变化后需要完整走一遍初始化验证

## 7. 测试执行建议

- 先从 `FR-001` 对应的生成能力开始写失败测试
- 再补 `FR-002` 和 `FR-003` 的文档质量与追踪关系检查
- 工具没定下来时，先把断言和验证路径写清楚

## 8. 完成定义

- 每个高优先级需求至少有一种自动化验证
- 关键路径的失败场景有覆盖
- bug 修复必须补回归测试
- 测试命令可以被稳定重复执行
