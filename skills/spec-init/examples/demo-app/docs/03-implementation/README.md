# Implementation Plan: Demo App

> 更新时间：2026-05-20
>
> 这份文档安排交付顺序，不替代设计文档。

## 1. 实施目标

先交付一套真正可用的 agent spec 工作流说明和示例文档，再补足现有项目补 spec 的案例与追踪关系，确保用户不是只拿到空结构。

## 2. 里程碑

| Milestone | 目标 | 输入 | 输出 | 验收方式 |
|---|---|---|---|---|
| `M1` | 明确 agent 驱动 spec 的主工作流 | 用户目标、现有项目场景、文档边界 | 更新后的 SKILL、README、示例文档 | 用户能理解这不是脚本脚手架 |
| `M2` | 补齐追踪关系与示例内容 | `M1` | `FR` / `DES` / `TEST` / `T` 完整链路、示例文档 | 至少一条链路可直接展示 |

## 3. 建议顺序

1. 先明确 skill 的真实定位和用户场景
2. 再完善 requirements、design、tdd、tasks 的追踪关系
3. 最后检查 README、AGENTS、rules 和示例是否与定位一致

## 4. 依赖关系

| 项目 | 依赖 | 说明 |
|---|---|---|
| spec 工作流说明 | SKILL + README | 没有工作流说明，用户会误解 skill 职责 |
| 规则目录输出 | 规则模板 | 没有规则目录，文档驱动开发约束不完整 |
| 追踪链建立 | requirements + design + tdd | 必须先有文档 ID 才能回链到任务 |

## 5. 高风险优先项

- 先验证 skill 定位是否清楚，避免用户继续把它理解成脚本工具
- 先验证示例是否能展示“agent 写 spec”而不是“脚本造目录”

## 6. 文档与测试同步计划

- 当模板结构变化时，同步更新 `docs/02-design/README.md` 中的承接说明
- 当新增高优需求时，先补 `docs/04-tdd/README.md` 的映射，再扩展任务清单
- 当目录结构变化时，同步更新 `README.md`、`AGENTS.md` 和 `docs/rules/`
- 当用户补充更多业务细节后，继续回写 `docs/01-requirements/README.md` 和 `docs/02-design/README.md`
- 当实现暴露新边界或新风险后，继续补 `docs/04-tdd/README.md` 和 `docs/05-tasks/README.md`

## 7. 发布 / 回滚思路

- 发布方式：先内部验证定位，再逐步公开说明
- 回滚思路：如果新的定位说明不清楚，优先修正示例和 README，而不是回退到脚本优先路径

## 8. 追踪落地计划

- `M1`: 先落 `FR-001 -> DES-001 -> TEST-001 -> T-001`
- `M2`: 再补 `FR-002`、`FR-003` 和 `FR-004` 的设计、测试和任务链路
- 下一版再补“现有项目补 spec”专项示例和 `service` / `library` 场景

## 9. 实施计划自检

- 这里安排的是交付顺序，不是重新做设计
- 高风险和高不确定性被前置验证
- 每个里程碑都有可观察的验收产出
- 文档更新和测试补齐已经被纳入计划
- spec 被当成持续更新的项目资产，而不是初始化时写一次就结束

## 10. 阻塞项与待确认

- 是否需要补一个完整的现有项目增量补文档示例
- 是否需要减少示例项目里对脚本资源的可见度
