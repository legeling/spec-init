# Requirements: Demo App

> 更新时间：2026-05-20
>
> 这份文档只写 what / why，不写 how。

## 1. 需求摘要

Demo App 需要把一个模糊想法或一个已有项目转成结构化 spec，帮助开发者在编码前先澄清目标、设计方案、测试策略、执行任务和默认工程规则。第一版重点是让 agent 真正写出有内容的 intake、requirements、design、tdd、tasks 和 rules，而不是只创建目录或空模板。

## 2. 用户故事

- `US-001` 作为独立开发者，我希望输入一个项目想法后，agent 能直接帮我整理第一版 spec，而不是只给我空模板。
- `US-002` 作为已有项目维护者，我希望 agent 能先读代码再补 design、tdd 和 tasks，而不是凭模板假设我的项目结构。

## 3. 功能需求

| ID | 描述 | 为什么需要 | 优先级 |
|---|---|---|---|
| `FR-001` | 用户能够让 agent 直接产出有内容的 spec，而不是只有空模板 | 避免“有文档结构但没有可用内容” | H |
| `FR-002` | 用户能够在信息不足时得到候选方案、对比和建议 | 帮助新手和非新手都更快做出关键决策 | H |
| `FR-003` | 对已有项目，agent 能先读现状再补齐 spec | 避免文档与真实代码脱节 | H |
| `FR-004` | 用户能够得到至少一条从需求到测试再到任务的追踪链和项目级规则 | 让文档成为可执行工作流，而不是孤立说明文件 | H |

## 4. 非功能需求

| ID | 描述 | 度量方式 |
|---|---|---|
| `NFR-001` | spec 内容应尽量反映真实上下文，而不是套模板瞎写 | 人工抽查 spec 是否与用户输入或现有项目一致 |
| `NFR-002` | 输出内容应能帮助新手理解概念，也能帮助老项目补齐文档 | 每份核心文档都包含提示、对比、示例或待确认项 |

## 5. 验收标准

| ID | 对应需求 | 验收条件 |
|---|---|---|
| `AC-001` | `FR-001` | 当用户只给出简短项目描述时，agent 产出的核心 spec 里应已有真实可读内容，而不只是标题 |
| `AC-002` | `FR-002` | 当关键设计点缺失时，文档中应出现方案、利弊、风险和推荐意见 |
| `AC-003` | `FR-003` | 面对已有项目时，spec 中应体现对现有结构、模块或调用链的归纳 |
| `AC-004` | `FR-004` | 示例项目中应至少存在一条 `FR-001 -> DES-001 -> TEST-001 -> T-001` 链路，以及关键规则文件 |

## 6. 优先级与版本边界

| Requirement | 优先级 | 目标版本 | 说明 |
|---|---|---|---|
| `FR-001` | H | V1 | 没有真实 spec 内容，skill 就没有实际价值 |
| `FR-002` | H | V1 | 方案对比和建议是新手最需要的帮助 |
| `FR-003` | H | V1 | 现有项目补 spec 是高频真实场景 |
| `FR-004` | H | V1 | 没有追踪链和规则，文档驱动开发会退化为空话 |

## 7. 范围外内容

- 不直接替代业务代码开发
- 不假装只靠模板就能完成需求分析和设计

## 8. 外部依赖与约束

- 依赖 agent 读取用户输入、代码库和现有文档
- 模板和脚本只作为辅助资源，可选使用

## 9. 需求自检

- 每条 `FR-*` 都能被单独验证
- 每条高优需求至少对应一个 `AC-*`
- 这里没有写技术栈、数据库、组件划分、接口实现细节
- 读完这份文档，不看代码也知道“项目要做什么”

## 10. 待确认

- 是否需要补一个“现有项目补 spec”的完整例子
- 是否要把 `service` / `library` 的场景细化到和 `web` / `api` / `cli` 同等级

## 不该写进这里的内容

- 技术栈名称
- 表结构和字段设计
- 类名、函数名、文件名
- API 路径细节
- 组件拆分方案
