# Design: Demo App

> 更新时间：2026-05-20
>
> 这份文档解释 how，不再重复 why。

## 1. 设计目标

- 为了满足 `FR-001`，系统需要具备一键生成阶段目录、规则目录和基础文件的能力。
- 为了满足 `FR-002` 和 `FR-003`，系统需要把需求、设计、测试和任务的边界与关联关系显式写入模板和示例。
- 为了满足 `FR-004`，系统需要把默认工程规则写成可读、可维护的文档资产。

## 2. 系统边界

- 输入：用户提供的项目名称、路径、项目类型、输出语言和项目描述
- 输出：目录结构、文档模板、规则模板、README、AGENTS、示例文档
- 外部系统：无强依赖，仅依赖本地 Bash 环境
- 不在本系统内的内容：具体业务代码实现、框架专有配置生成

## 3. 架构概览

系统由四个主要部分组成：

- 初始化脚本：负责生成目录、规则和基础文件
- 模板资源：负责提供每份文档的结构、提示和自检项
- 规则模板：负责沉淀编码、测试、文档同步和完成定义要求
- 参考示例：负责展示一条完整的文档追踪链应该长什么样

## 3.1 候选方案与用户确认

| 议题 | 方案 | 优点 | 代价 / 风险 | 推荐意见 | 是否已获用户确认 |
|---|---|---|---|---|---|
| 模板生成方式 | Bash + 模板文件 | 轻量、可移植、易维护 | 复杂交互能力弱 | 当前推荐，用于第一版快速稳定交付 | 是 |
| 模板生成方式 | 交互式 Node CLI | 交互体验更丰富 | 成本更高、依赖更多 | 暂不推荐作为第一版 | 否 |

## 4. 模块设计

| ID | 模块 | 职责 | 对应需求 |
|---|---|---|---|
| `DES-001` | Scaffold Generator | 创建阶段目录、规则目录、复制模板、替换项目名和类型 | `FR-001` |
| `DES-002` | Documentation Templates | 为 intake、requirements、design、plan、tdd、tasks 提供结构和边界提示 | `FR-002` |
| `DES-003` | Traceability Example | 提供最小完整示例，展示文档如何从需求贯穿到任务 | `FR-003` |
| `DES-004` | Rule Templates | 为 coding、testing、doc sync、DoD 提供默认规则 | `FR-004` |

## 5. 数据与状态

- 核心实体：项目名、项目类型、输出语言、模板文件、输出文件
- 关键字段：`project_name`、`project_type`、`language`、`date`
- 状态转换：从“空目录”进入“已初始化”，再进入“文档已补充”状态

## 6. 接口与契约

| 接口 | 输入 | 输出 | 错误场景 | 对应需求 |
|---|---|---|---|---|
| `spec-init.sh` | 目标路径、项目名、项目类型、输出语言、是否覆盖 | 生成后的项目骨架 | 路径无权限、参数冲突、模板缺失 | `FR-001` |

## 7. 技术决策与权衡

- 决策：使用轻量模板 + Bash 脚本的方式初始化项目，而不是做重型交互式生成器
- 备选方案：只给 README、只给 docs 模板、或者直接生成业务代码
- 为什么不选：只给 README 过于弱；直接生成业务代码会把问题从“澄清需求”变成“猜需求”

重要决策建议同步记录到 `docs/adr/`。

## 7.1 技术栈与基础设施

- 前端 / 客户端：无
- 后端 / 服务端：Bash 脚本
- 数据存储：模板文件系统
- 测试框架：Bash smoke tests + CI
- 部署形态：本地脚本 / skill 资源目录

说明：

- 这里选择 Bash，是因为当前目标是“最大兼容性 + 最小依赖 + 易于在多宿主中复用”。
- 如果未来需要更复杂交互，再评估是否演进为更重的 CLI 工具。

## 7.2 架构质量目标

- 可维护性：模板目录要清晰分层，中英文字段和类型化模板可独立维护
- 性能目标：初始化脚本应在秒级完成
- 安全目标：禁止输出误导性规则，不允许用默认值掩盖关键信息缺失
- 可测试性：脚本和模板输出必须能通过白盒 / 集成 / 回归检查验证
