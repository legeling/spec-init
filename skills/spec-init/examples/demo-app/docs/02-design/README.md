# Design: Demo App

> 更新时间：2026-05-20
>
> 这份文档解释 how，不再重复 why。

## 1. 设计目标

- 为了满足 `FR-001`，系统需要让 agent 能直接写出第一版可用 spec，而不是只输出空模板。
- 为了满足 `FR-002`，系统需要在关键缺失信息处主动给出候选方案、利弊和推荐意见。
- 为了满足 `FR-003`，系统需要支持“先读现有项目，再补文档”的工作流。
- 为了满足 `FR-004`，系统需要把追踪关系和项目级规则沉淀成可执行文档资产。

## 2. 系统边界

- 输入：用户请求、现有仓库结构、已有代码、已有文档、项目描述
- 输出：更新后的 spec、README、AGENTS、规则说明、待确认项和追踪链
- 外部系统：宿主提供的文件读取、搜索和编辑能力
- 不在本系统内的内容：代替用户完成全部业务实现

## 3. 架构概览

系统由四个主要部分组成：

- agent 工作流：负责理解需求、读取现状、归纳 spec、输出待确认问题
- 模板资源：负责提供每份文档的结构、提示和自检项
- 规则模板：负责沉淀编码、测试、文档同步和完成定义要求
- 参考示例：负责展示一条完整的 spec 追踪链应该长什么样

## 3.1 候选方案与用户确认

| 议题 | 方案 | 优点 | 代价 / 风险 | 推荐意见 | 是否已获用户确认 |
|---|---|---|---|---|---|
| spec 产出方式 | agent 直接写内容 | 结果更贴近用户上下文和项目现状 | 对 agent 能力要求更高 | 当前推荐 | 是 |
| spec 产出方式 | 只靠脚本和模板生成 | 落地快、结构稳定 | 容易变成空文档 | 不推荐作为主路径 | 否 |

## 4. 模块设计

| ID | 模块 | 职责 | 对应需求 |
|---|---|---|---|
| `DES-001` | Spec Authoring Workflow | 基于用户目标或现有项目现状编写有内容的 spec | `FR-001`, `FR-003` |
| `DES-002` | Decision Guidance Layer | 在关键信息缺失时提供候选方案、对比和建议 | `FR-002` |
| `DES-003` | Traceability Layer | 建立 requirements、design、tests、tasks 之间的追踪链 | `FR-004` |
| `DES-004` | Rule Templates | 为 coding、testing、doc sync、DoD 提供默认规则 | `FR-004` |

## 5. 数据与状态

- 核心实体：用户目标、项目现状、文档条目、待确认项、追踪 ID
- 关键字段：`project_type`、`known_context`、`open_questions`、`FR/DES/TEST/T IDs`
- 状态转换：从“模糊请求或缺失文档”进入“第一版 spec 已形成”，再进入“持续更新”状态

## 6. 接口与契约

| 接口 | 输入 | 输出 | 错误场景 | 对应需求 |
|---|---|---|---|---|
| `spec-init skill` | 用户请求、代码上下文、现有文档、项目目标 | 更新后的 spec 与规则文档 | 现状读取不全、关键信息未确认、追踪链断裂 | `FR-001`, `FR-002`, `FR-003`, `FR-004` |

## 7. 技术决策与权衡

- 决策：把 agent 直接写 spec 作为主路径，模板和脚本只作为辅助
- 备选方案：继续把 skill 定位成目录初始化器
- 为什么不选：那样很容易得到“有结构没内容”的结果，无法真正帮助用户做文档驱动开发

重要决策建议同步记录到 `docs/adr/`。

## 7.1 技术栈与基础设施

- 前端 / 客户端：无固定要求，依赖宿主交互界面
- 后端 / 服务端：无独立服务，主要依赖 agent 和宿主工具链
- 数据存储：仓库中的 markdown 文档、规则文件和参考资源
- 测试框架：文档回归检查 + skill 行为验证
- 部署形态：agent skill 资源目录

说明：

- 这里不把 Bash 脚本当主能力，因为真正价值在于 agent 的理解、分析和写作。
- 模板和脚本仍保留，作为空项目下的辅助资源，而不是最终交付。

## 7.2 架构质量目标

- 可维护性：工作流说明、模板资源、示例和规则要彼此一致
- 性能目标：单轮内能产出高质量第一版 spec，而不是堆空文档
- 安全目标：禁止编造项目现状，禁止把推荐写成确认，禁止默认掩盖未确认信息
- 可测试性：文档、示例、规则和真实使用场景都能被回归验证

## 8. 需求映射说明

- `DES-001` 直接承接 `FR-001`
- `DES-002` 直接承接 `FR-002`
- `DES-003` 直接承接 `FR-003`
- `DES-004` 直接承接 `FR-004`

## 9. 风险与缓解

- 风险：skill 继续被理解成“脚本造模板”，导致用户觉得没有实际价值
- 缓解：把 agent 驱动 spec 写作明确成主路径，并提供现有项目补 spec 的示例
