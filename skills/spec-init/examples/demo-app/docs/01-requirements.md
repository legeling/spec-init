# Requirements: Demo App

> 更新时间：2026-04-29
>
> 这份文档只写 what / why，不写 how。

## 1. 需求摘要

Demo App 需要把一个模糊的项目想法转成结构化文档骨架，帮助开发者在编码前先澄清目标、设计方案、测试策略和执行任务。第一版重点是生成项目目录、README、AGENTS 以及 docs 下的核心文档，并指导用户区分需求和设计。系统不直接实现业务功能，而是优先提供文档化启动能力。

## 2. 用户故事

- `US-001` 作为独立开发者，我希望输入一个项目想法后就能得到完整的初始化文档骨架，以便我快速开始项目而不是卡在空白页。
- `US-002` 作为新手开发者，我希望文档能明确告诉我需求和设计分别写什么，以便减少误解和返工。

## 3. 功能需求

| ID | 描述 | 为什么需要 | 优先级 |
|---|---|---|---|
| `FR-001` | 用户能够一键生成包含 `docs/`、`README.md`、`AGENTS.md`、`src/`、`tests/`、`scripts/` 的项目骨架 | 让项目可以立即进入规范化启动阶段 | H |
| `FR-002` | 用户能够获得区分需求文档与设计文档的模板和写作提示 | 帮助新手减少“把技术方案写进需求”的常见错误 | H |
| `FR-003` | 用户能够得到至少一条从需求到测试再到任务的示例追踪链 | 让文档不是孤立文件，而是可执行工作流 | H |

## 4. 非功能需求

| ID | 描述 | 度量方式 |
|---|---|---|
| `NFR-001` | 初始化输出应该在单次运行中稳定生成，不要求用户手动补目录 | 实测一次初始化后所有核心文件均存在 |
| `NFR-002` | 模板内容应该能被新手直接编辑，而不是只有标题 | 每份核心文档至少包含写作提示、自检项或示例占位 |

## 5. 验收标准

| ID | 对应需求 | 验收条件 |
|---|---|---|
| `AC-001` | `FR-001` | 当用户运行初始化后，应出现 docs、README、AGENTS、src、tests、scripts 六类核心产物 |
| `AC-002` | `FR-002` | 当用户阅读 requirements 和 design 模板时，应能看到“该写什么”和“不该写什么” |
| `AC-003` | `FR-003` | 示例项目中应至少存在一条 `FR-001 -> DES-001 -> TEST-001 -> T-001` 链路 |

## 6. 优先级与版本边界

| Requirement | 优先级 | 目标版本 | 说明 |
|---|---|---|---|
| `FR-001` | H | V1 | 没有骨架就无法开始 |
| `FR-002` | H | V1 | 这是新手最容易混淆的核心能力 |
| `FR-003` | H | V1 | 没有追踪关系，这套方法论就落不了地 |

## 7. 范围外内容

- 不自动生成具体业务模块代码
- 不根据某个前端或后端框架输出专有实现

## 8. 外部依赖与约束

- 需要 Bash 环境执行初始化脚本
- 文档模板默认中文输出

## 9. 需求自检

- 每条 `FR-*` 都能被单独验证
- 每条高优需求至少对应一个 `AC-*`
- 这里没有写技术栈、数据库、组件划分、接口实现细节
- 读完这份文档，不看代码也知道“项目要做什么”

## 10. 待确认

- 是否需要按项目类型输出不同模板内容
- 是否要支持更多语言版本
