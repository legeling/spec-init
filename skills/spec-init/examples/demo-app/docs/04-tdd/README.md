# TDD Plan: Demo App

> 更新时间：2026-05-20
>
> 先定义如何证明正确，再开始大规模实现。

## 1. 测试目标

- 先验证 skill 是否真的驱动 agent 写出有内容的 spec
- 先验证文档之间的追踪关系没有断链

## 2. 测试层次

| 层次 | 目标 | 覆盖内容 | 工具 / 方式 |
|---|---|---|---|
| White-box Unit | 验证文档规则与边界说明的一致性 | 文档边界、待确认、追踪关系、自检项 | 文档检查 |
| Integration | 验证 skill 资源组合后能支撑真实 spec 写作 | SKILL、README、示例、rules、模板资源 | 人工 walkthrough + 回归检查 |
| E2E | 验证用户从想法到首批任务的完整路径 | intake -> requirements -> design -> tdd -> tasks | 人工 walkthrough + 示例文档 |
| Performance | 验证单轮整理 spec 的成本可接受 | 文档规模、阅读和更新路径 | 手动评估 |
| Security | 验证规则和输出不误导用户 | 关键疑点确认规则、未确认信息处理、推荐与确认区分 | 文档审查 + 回归检查 |

## 3. 需求到测试映射

| Test ID | Requirement | Test Type | 核心断言 |
|---|---|---|---|
| `TEST-001` | `FR-001` | E2E | 示例应明确体现 agent 直接写 spec，而不是只生成模板 |
| `TEST-002` | `FR-002` | E2E | 文档中应显式写出候选方案、对比与推荐 |
| `TEST-003` | `FR-003` | E2E | 示例中应体现现有项目补 spec 的要求或待补案例 |
| `TEST-004` | `FR-004` | Integration | 示例中应存在 rules 目录及完整追踪链 |

要求：

- 每个高优先级 `FR-*` 至少映射到一种自动化测试
- 与当前版本相关的白盒、性能、安全测试必须进入计划
- 如果某条需求暂时不能自动化验证，要写清原因和替代验证方式

## 4. 第一批红灯测试

1. 示例仍然把 skill 写成脚本初始化器
2. 文档里没有区分“推荐”和“已确认”
3. 示例里找不到 `FR -> DES -> TEST -> T` 链路
4. rules 中没有体现现有项目补 spec 的约束

## 5. 测试数据与夹具

- 一个只有模糊需求描述的新项目场景
- 一个已有 README / docs / 代码的现有项目场景

## 5.1 白盒测试重点

- 追踪链回写逻辑
- 推荐与确认的表述边界
- 现有项目优先读取再写文档的约束

## 5.2 性能测试计划

- 关键性能指标：单轮能否产出足够可用的第一版 spec
- 压测场景：面对已有项目时，阅读和归纳成本是否失控
- 通过标准：在合理上下文规模下仍能产出可执行 spec

## 5.3 安全测试计划

- 关键疑点确认规则是否清晰可见
- 模板是否鼓励用户直接猜测需求或架构
- 输出内容是否会默认掩盖未确认信息

## 6. 回归策略

- README、SKILL、示例和 rules 的定位必须保持一致
- 任何文档边界改动都要补回归检查
- 每次定位调整后都要检查示例是否还在误导用户

## 7. 测试执行建议

- 先从 `FR-001` 对应的真实 spec 产出能力开始验证
- 再补 `FR-002`、`FR-003` 和 `FR-004` 的对比质量、现有项目支持和追踪关系检查
- 工具没定下来时，先把断言和验证路径写清楚

## 8. 完成定义

- 每个高优先级需求至少有一种自动化验证
- 关键路径的失败场景有覆盖
- bug 修复必须补回归测试
- 测试命令可以被稳定重复执行
- 白盒、性能、安全要求已被显式检查或标明延期原因
