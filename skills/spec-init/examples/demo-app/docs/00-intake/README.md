# Project Intake: Demo App

> 项目类型：web
>
> 更新时间：2026-05-20
>
> 这份文档只澄清问题，不做技术方案。

## 1. 一句话描述

Demo App 帮助个人开发者把零散的项目想法快速整理成需求、设计、测试、任务和项目规则文档，再进入实现阶段。

## 2. 背景问题

- 当前现状：很多个人开发者或新手一开始就直接写代码，项目目标、边界、测试策略和默认规则都不清楚。
- 主要痛点：需求和设计混在一起，开发到一半才发现理解错了；规则只存在聊天里，后续很快失效。
- 为什么现在要做：在项目启动阶段补齐文档骨架和规则目录，能显著降低返工并帮助后续协作。

## 3. 目标用户

| 用户类型 | 他们是谁 | 他们最在乎什么 |
|---|---|---|
| 独立开发者 | 自己从 0 到 1 做项目的人 | 尽快理清项目目标和第一步开发顺序 |
| 新手开发者 | 还不清楚需求、设计、测试和规则区别的人 | 有模板、有示例、知道每份文档该写什么 |

## 4. 关键场景

1. 用户输入一句项目想法，希望自动生成文档骨架和规则目录
2. 用户不清楚需求和设计区别，希望得到明确拆分
3. 用户想用 TDD 开始项目，但不知道第一批测试和默认规则该怎么列

## 5. 成功标准

- 10 分钟内能生成一套完整的初始化文档和规则骨架
- 至少形成一条 `FR -> DES -> TEST -> T` 的可追踪链路
- 新成员看完 README 和 docs 后，能理解项目第一阶段要做什么，以及默认应该怎么做

## 6. 非目标

- 不直接生成完整业务代码
- 不替代具体技术栈实现细节讨论

## 7. 约束

- 时间：项目启动当天即可使用
- 平台：Web 项目初始化场景
- 合规 / 安全：无特殊要求
- 性能：初始化脚本应在秒级完成
- 预算 / 人力：单人项目优先

## 8. 假设与风险

- 假设 1：用户愿意先写文档再编码，而不是直接跳进实现
- 风险 1：如果模板太空，用户仍然不知道如何填写

## 9. 当前推断

- 当前推断的项目类型：`web`
- 推断依据：用户明确通过命令参数指定项目类型：web。
- 这里是示例项目，不代表所有真实项目都应选 `web`

## 10. Intake 自检

- 这份文档在描述问题和目标，而不是技术方案
- 这里已经说明谁会使用、为什么现在做、什么不做
- 这里至少有一组可衡量成功标准
- 读完后，别人能理解这个项目为什么值得做

## 11. 待确认问题

- 是否需要为 `service` / `library` 增加更多专门模板
- 是否要继续补一个英文版示例项目
- 是否需要给 rules 增加更细的代码审查规则
